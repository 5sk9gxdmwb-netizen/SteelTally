## 精确签名合约

1. RSA 2048–4096 位，模数长度必须等于 bitLength/8，指数 1–8 字节；RSA PKCS#1 v1.5 填充，摘要 SHA-256。此处不是 RSA-PSS，也不是 Authenticode。
2. 公钥使用 **BCrypt `BCRYPT_RSAPUBLIC_BLOB`**（`BCryptImportKeyPair` 类型 `RSAPUBLICBLOB`），不是旧 CryptoAPI `PUBLICKEYBLOB`、PEM、DER、证书或私钥 blob。
3. Blob 为 6 个 little-endian uint32：`Magic=0x31415352`（RSA1）、`BitLength`、`cbPublicExp`、`cbModulus`、`cbPrime1=0`、`cbPrime2=0`，紧接 big-endian unsigned 公钥指数和模数。整体再标准 Base64 后用于构建配置。
4. 先生成 UTF-8 payload JSON 的**最终字节串**，对这些精确字节计算 SHA-256，再调用 RSA PKCS1/SHA256 签名。不能在签名后更改空白、换行、字段顺序、转义或编码。签名是大端 RSA 签名原始字节（BCrypt 和 .NET RSA.SignData 原样输出）。
5. 将 payload 原始字节和签名分别标准 Base64，装入外层 JSON。客户端先验签，再解析 payload；签名只覆盖解码后的 payload，不覆盖外层排版。不能在客户端重新序列化 payload 后验签。
6. 外层仅允许 `payload`、`signature` 两个 string；两层都拒绝未知字段、重复字段（包括 JSON 转义后同名）、缺字段、错误类型、无效 JSON 和非规范 Base64。禁止服务器提供替代 key、算法或证书。

外层示例：

```json
{"payload":"<UTF-8 payload bytes的Base64>","signature":"<RSA PKCS1 SHA256签名的Base64>"}
```

Payload 示例（实际 size 和 SHA256 必须来自最终 EXE；下面值只是格式示例）：

```json
{
  "schema": "steeltally.update/1",
  "version": "1.0.4",
  "url": "https://updates.example.invalid/steeltally/gjg_table_qty.exe",
  "size": 60000000,
  "sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "notes": "本次更新内容",
  "catalog_version": "1.0.3",
  "rules_version": "1.0.3",
  "project_schema": "1"
}
```

所有九个字段必填。`size` 为 1 到 536870912 的整数，`sha256` 为 64 位小写 hex。notes 最长 8192 字符；URL 最长 2048 字符；三个组件版本字段为 1–128 字符的说明文本。清单 envelope 上限 96 KiB，payload 上限 32 KiB。软件版本仅支持三段非负十进制，每段 0–999999，不允许多余前导零、预发布或 build 后缀，按三段数字比较；不把版本当浮点数或字符串排序。只安装严格高于当前 EXE 版本的清单，拒绝降级和不合法版本。

发布方在受控离线/签名环境取得 `$rsa`（含私钥的 .NET RSA 对象）后，可采用如下核心调用。该流程仅为合约示例，项目不持有发布私钥：

```powershell
$raw = [Text.Encoding]::UTF8.GetBytes($finalPayloadJson)
$sig = $rsa.SignData($raw,
    [Security.Cryptography.HashAlgorithmName]::SHA256,
    [Security.Cryptography.RSASignaturePadding]::Pkcs1)
$envelope = @{
    payload = [Convert]::ToBase64String($raw)
    signature = [Convert]::ToBase64String($sig)
} | ConvertTo-Json -Compress
[IO.File]::WriteAllText($manifestPath, $envelope,
    (New-Object Text.UTF8Encoding($false)))
```

EXE、内嵌目录和帮助随整包一起替换。先上传完整 EXE，再发布匹配清单。公钥轮换必须通过已经受信的旧版本发布流程更新嵌入密钥；服务器不能自行换 key。

## 下载、安全限制和安装事务

- Qt 异步 HTTPS；使用系统 TLS 信任链，不调用 ignoreSslErrors；使用受控 ManualRedirectPolicy，每次3xx结束后验证目标并新建HTTPS请求，累计最多5次；共用全事务计时器与数据sink。独立 manager 禁用认证复用，deny-all cookie jar 禁止 cookie 保存/转发。单次无传输进展超时 60 秒，清单总时限 30 秒，EXE 总时限十分钟，可取消。只接受 HTTP 200，限定内存读缓冲和写入总量；超限、中断、TLS、超时及磁盘写入失败均不安装。
- 每次下载在 OS temp 直接子目录 `SteelTally-update-<UUID>`，以 NewOnly 打开 `download.exe`；不使用服务器文件名。完整文件按签名清单检查大小、SHA256 和 MZ 头；在安装前、helper 开始、等待父进程结束后以及复制到目标目录之后再次校验相应文件。
- 将当前同一 EXE 复制为该目录的 `helper.exe`，仅用显式 CreateProcessW 路径启动 `--update-helper <stage>`。无 shell、脚本或任意命令。拒绝其他参数数量、非 temp 直接子目录、错误 UUID、相对路径、重解析点/链接、错误 helper 路径。
- 事务记录精确目标 canonical EXE 路径、PID、Windows 进程创建 FILETIME、随机 nonce，以及仅允许的绝对 `--data-root`。helper 比较父进程的真实映像路径和创建时间，比较 helper/目标 SHA256。不会按进程名称批量终止，也不接受任意重启参数。
- helper 持有确切父进程句柄后写 ready；主程序异步等候最多 15 秒，仅观察到匹配 nonce 后退出。未就绪则终止自己刚启动的 helper，保留当前程序。helper 最多等父进程 120 秒，超时不替换。
- 先在目标同一目录创建唯一 `.update-new-<UUID>.exe`，再次验证，再用 Windows ReplaceFileW 替换并创建 `.update-backup-<UUID>.exe`。需要该目录写权限；没有权限则记录失败，不提升权限、不触碰项目或设置。
- 启动新版，传入内部 `--update-health <stage> <nonce>` 及原有自定义 `--data-root`。主窗口创建并显示、事件循环运行三秒后才写匹配 health；helper 最多等候 45 秒，收到后再观察进程存活五秒。未健康则停止自己启动的新进程，保留失败 EXE 为 `.update-failed-<UUID>.exe`，恢复备份并重启旧版。
- 保留旧 EXE、失败 EXE、暂存文件、日志与 result.json 供用户手动归档/删除，不自动永久删除。更新只操作精确 EXE 及上述自身生成文件；不会清空工程、user-data、企业库或 QSettings。
- 诊断在暂存目录 `update.log` / `result.json`；无暂存目录的检查失败写入 Windows AppLocalDataLocation 的 `updater-logs/update.log`。helper 返回 20/21 为参数/路径拒绝，22 为事务/校验/替换失败，25 为健康失败但已回滚，26 为回滚失败。

此机制验证发布密钥持有者对清单及 EXE 哈希的授权，不等同于 Windows 发布者代码签名。写入用户可写目录的同权限恶意进程或管理员不属于本更新器可防御的安全边界；不要把 temp 当跨用户安全沙箱。ReplaceFileW 与回滚减少运行期故障影响，但不能保证突然断电、磁盘故障或进程在替换后被强行杀死时自动恢复。保留备份便于人工恢复；健康握手证明主窗口和事件循环启动，不是完整业务正确性认证。

## 2026-11-10 HTTPS 跳转修复

`Transfer` 是 Controller 与 `--update-network-test <新证据目录>` 的共享请求和数据流。该 CLI 只用生产内嵌公钥读取稳定清单、验签、下载签名附件并验证 size/SHA256/MZ；忽略版本比较用于验收已上线旧附件，绝无安装调用，也不接受覆盖公钥参数。结果为目录内 result.json，保留 manifest.json 和 download.exe，不记录签名查询串。

Qt 6.8.3 源码检查：qhttpthreaddelegate.cpp finishedSlot 在发 redirected 之前可能发送 downloadData；qnetworkreplyhttpimpl.cpp followRedirect 清除响应 headers。因此 readyRead 和 finished 尾部均经过共享 consume，仅 HTTP 200 能写入 sink；3xx body 丢弃且不计入最终文件/清单。自测直接调用同一 consume 覆盖 302/307 body、最终 200、超限和取消，并覆盖 HTTP、credentials、坏 URL、fragment、非443、第五/第六次跳转边界。没有以自签证书绕过 TLS。

构建时如当前 release-static 正在运行，使用 `-PublishDirectory <独立目录>` 保留用户窗口与旧包，候选包验收后由用户选择切换。当前最终候选路径为 release-static-redirect-fixed/gjg_table_qty.exe。历史证据章节保留原记录，不代表当前包的配置。

### Schannel 根因及最终修补

最小probe的受控对照：动态默认OpenSSL完整通过，动态强制Schannel及原静态Schannel均停顿；原静态即使不限制reply buffer也失败。底层脱敏计数在65536字节解密buffer排空后显示intermediate=8/missingData=16398/plain=0。Schannel在等足missingData之前不消费底层QTcpSocket部分数据，可能与底层buffer形成等待。

独立SDK补丁仅去掉transmit循环中这个提前等待，使已有readToBuffer按16KiB吸收部分record。DecryptMessage及SEC_E_INCOMPLETE_MESSAGE未改变，原hadIncompleteData && bytesRead==0仍退出，没有busy-spin或证书绕过。补丁后同静态Schannel最小probe 7695ms完整58,834,192字节、Qt0、HTTP200、一次302。原SDK/源码完整保留；新SDK C:/SteelTallySchannelDiagnostic/install，补丁/原件/重编脚本/哈希及许可关联在distribution-materials/schannel-partial-record-fix。最终应用恢复15秒无进展、30秒清单、十分钟附件总时限，未保留TLS1.2/HTTP1.1或定时pump试验。
